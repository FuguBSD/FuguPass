# Decisions

This document holds the decisions that govern FuguPass.
A plan must not go against a decision.
To change a decision, propose the change and get human approval first.

| ID | Decision | Rationale |
| --- | --- | --- |
| D-01 | One vault has one master. The master is a BIP39 mnemonic of 12 words. Every vault key derives from the master. FuguPass must not implement a share split of the master. | One root gives one recovery object: one plate restores the vault. A share split needs an encoding choice and a share-generation analysis that do not exist. A change to this decision needs that analysis and human approval. |
| D-02 | All custody and policy logic lives in the client. FuguPass must speak unmodified blind_pin_server protocol v2 to any conforming oracle. FuguPass must not require a change to FuguOracle. FuguOracle is the reference deployment, not a requirement. | The oracle stays small, generic, and blind to policy. The upstream Python server is a valid counterparty for development and test. FuguPass proves the FuguOracle claim that the oracle serves more clients than the Jade. |
| D-03 | An oracle-side policy feature requires an approved FuguOracle decision change before any FuguPass work assumes it. The specification must not assume a delayed reveal, a velocity alarm, a freeze operation, or any oracle behavior beyond protocol v2 as the FuguOracle specification states it. | The FuguOracle specification defines junk, strike, and wipe semantics exactly. A policy feature changes that specified behavior, so it goes through FuguOracle governance, not around it. |
| D-04 | The oracle gates reveals only. The oracle must not gate recovery. The plate alone must restore every derived and sovereign entry. The plate plus any copy of the vault files must restore every stored entry. | The oracle can disappear, be seized, or wipe. The user loses a reveal flow, never data. This matches the oracle design, where the recovery phrase works after a wipe. |
| D-05 | Each entry has an origin class: derived by default, stored for imports, sovereign for own-plate secrets, and shadow for metadata-only records. The origin class sets the secret origin, the backup medium, and the restore path. | The classes differ in backup and restore semantics. Every class reveals through the same oracle gate, so origin and custody stay orthogonal. |
| D-06 | Every entry reveal is gated by the vault passphrase plus any k of the n oracle masks for that entry (D-20). The factor inputs of a reveal must not coexist at rest. FuguPass must not implement a reveal-policy grammar, a per-entry reveal policy, or a no-oracle reveal path. | The oracle quorum removes the silent offline bulk-loss case. A no-oracle wrap on disk is an offline passphrase verifier, and that verifier forfeits the custody claim. The threshold mechanism is the one vault-wide split of D-20, and the deterministic-share analysis gates it (D-19). A policy grammar multiplies constructions, and the design needs exactly one. |
| D-07 | Each entry uses one oracle record at each oracle of the set, on each machine. The client keys of a record derive from the device factor of that machine and carry the oracle index. A reveal is a per-entry event of k oracle requests, each against its own three-strike counter. | Per-record custody gives rate limiting, audit, revocation, and strike containment per secret, with nothing new on the wire. The oracle client model requires a keypair that does not depend on the reveal secret, or the attempt counter never moves. |
| D-08 | The client verifies the passphrase against a canary record before it touches an entry record. | A typo must not burn attempts on an entry record. The canary guards nothing derived from the master, so the client re-enrolls it at any time. |
| D-09 | The reveal secret is a passphrase of any length, never a numeric PIN. Every key that derives from a typed passphrase must pass through bcrypt_pbkdf(3) with a tunable round count. HMAC-family derivation takes high-entropy keys only. The documentation must state the offline-search floor. | An attacker with the disk and the oracle record searches the passphrase offline. The KDF sets the cost of that search. Passphrase quality sets the floor, and the documentation says so. |
| D-10 | The system RNG must not generate a stored secret. Long-term secrets come from dice or from derivation. The device factor derives from the master with per-machine domain separation. Ephemeral request keys, IVs, seal nonces, and enrollment entropy come from arc4random(3). | The rule stays exact with no exception. A derived device factor lets the plate regenerate any machine's client keys and record names. The owner can therefore revoke a stolen machine from the plate alone. |
| D-11 | The dice ceremony rolls two distinguishable d16 and one d8 for each word, eleven times, plus one d16-and-d8 roll for the final word. The tool computes only the checksum. | The 2048 outcomes map one-to-one to the wordlist, bias-free and hand-verifiable against a printed card. The ceremony yields the full 128 entropy bits. A signer with d6 support is an equal entropy source through SeedQR import. |
| D-12 | The master appears only during ceremonies: vault creation, pool refill, machine provisioning, plate verification, and recovery. Between ceremonies the master exists only on plates. Each ceremony pre-derives a pool of future entry slots, and a new entry consumes one slot. The default pool size is 64 slots. | A resident or cached master hands malware every entry key in one moment. The design removes that failure. Without the pool, every new entry needs a plate ceremony. That cost pushes the plate to the desk, or it pushes the design back to a cached master. The pool is the enrollment loop run in advance, with nothing new on the wire. |
| D-13 | The vault is a directory of flat files, one encrypted file per entry, with no database. The on-disk state splits into a shared set and a machine-local set. The shared set holds the entry files and the index. The machine-local set holds the device factor, the wraps, the counters, and the config, and must not move between machines. The seal is ChaCha20-Poly1305 from LibreSSL libcrypto, with a fresh arc4random(3) nonce for each write. | Flat files keep the code and the audit surface small. Every copy of a shared-set file is a safe backup. The wraps and the counters bind to one machine's device factor and oracle records, so a copy to another machine desynchronizes them. The decrypt failure of the seal is the client's own junk detector for oracle answers. |
| D-14 | Entry names and metadata are encrypted at rest. A directory listing must reveal nothing about the entries. An encrypted index file maps names to files. | Plaintext file names leak the user's accounts. The index is itself a sealed file, and the paper QR export answers index loss. |
| D-15 | The AEAD, curve, hash, and passphrase-KDF primitives come from LibreSSL libcrypto, libsecp256k1, and bcrypt_pbkdf(3) from libutil only. The GF(256) share arithmetic comes from a vetted ISC- or BSD-licensed implementation, or from an in-tree implementation whose full arithmetic the specification states and whose outputs match known-answer vectors from an independent reference implementation. QR and camera code lives in separate sandboxed helper programs. The vault process must not parse camera data. | Tested primitives with the exact wire semantics, and no reimplementation of wire cryptography. The share arithmetic is outside the closed primitive set, so it needs a recorded source evaluation and pinned vectors (QA-SPLIT). The camera and the QR codecs are the real parser attack surface, so they stay quarantined. |
| D-16 | The vault core and the helper programs are C in KNF for OpenBSD -stable, with the ISC license. The interface program is Perl on the Fugu library, and Fugu::REPL is its line editor. The interface process must not hold a secret. The project packages FuguPass as a port, with the Fugu distribution as a dependency. | FuguPass integrates with the OpenBSD base system and its ports tree, in the family line of the oracle. The C core keeps the memory-hygiene and primitive duties against libc, libcrypto, and libutil. The line editor and the command parser stay outside the secret path, so the interface can grow into a more comprehensive UX with fast and safe iteration: an interface change never touches the audited core. FuguTTX builds its operator REPL on the same Fugu::REPL module, so the interactive behavior stays uniform across the FuguBSD tools. |
| D-17 | Derived passwords come from BIP85 application PWD BASE64. Derived child mnemonics come from the BIP85 BIP39 application. The BIP85 index of an entry is its reserved slot index. The tool materializes derived secrets at ceremony time and seals them under the entry key. | The standard applications buy ecosystem compatibility. Ceremony-time materialization keeps the master out of daily life. Reference test vectors gate the implementation. |
| D-18 | Secrets print to the TTY or render as a QR code on the screen. FuguPass must not implement a clipboard, an agent process, or a network service other than the oracle client. | A clipboard and a resident agent add leak surfaces and dependencies that the initial version does not need. The REPL covers the session need. |
| D-19 | Acceptance of the oracle client is one interop harness that passes against every available conforming oracle, and against the upstream blind_pin_server at minimum. The FuguOracle leg is required when a FuguOracle build exists. Acceptance of the custody layer includes the mask-stability test, a human-approved written analysis of the mask composition, and a human-approved written analysis of the deterministic share split. | The stability of the oracle answer is a consequence of the oracle rules, not a stated interface guarantee, so a test pins it. The mask composition uses the answer beyond the protocol's analyzed purpose. The deterministic coefficients replace the uniform-coefficient assumption of the standard Shamir argument. Each construction needs its own written analysis. |
| D-20 | One vault has one ordered oracle set of n oracles and one threshold k, with 1 ≤ k ≤ n ≤ 255, both vault-wide and recorded in the config. Every split secret splits into n shares with threshold k, one share per oracle. The oracle index of an oracle is its 1-based position in the ordered list. The list must not reorder, and a removed oracle leaves a retired position. FuguPass must not implement per-entry thresholds or per-entry oracle sets. The documented example topology is 2-of-3. | The oracle index enters the derivation labels and the share evaluation points, so index stability is load-bearing. One vault-wide topology keeps one construction everywhere: with one oracle and k = 1, every share equals the secret, and the wrap is the plain wrap with no special case. The 2-of-3 example — a home box, a VPS, and a friend's box — gives one-loss availability over a two-breach offline-loss bound; one breach yields the passphrase verifier only. |
